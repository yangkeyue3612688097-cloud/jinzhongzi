## 1. 一页结论

### 1.1 一句话定位

> 面向 AI 创作者及 2-10 人创作团队，提供作品来源存证、版本校验、协作确权、协商分润、收入结算和公开验证。

### 1.2 一句话价值

> 不只证明“这张图是 AI 生成的”，而是把生成参数、文件指纹、版本、协作者确认、协议版本、收入事件和结算凭证组成一条可复核的责任链。

### 1.3 当前准确状态

当前已经打通以下本地业务闭环：

```text
ComfyUI 生成
  -> 自动采集参数和工作流哈希
  -> 服务端计算文件 SHA-256
  -> 规范化来源数据并生成存证哈希
  -> 创作者签名
  -> 来源清单 + PDF 存证证书 + 公开验证页
  -> 作品版本哈希与版本演进
  -> 邀请协作者并逐人确认协议
  -> 协议版本、比例和确认记录固化
  -> 授权订单 + 确认收款
  -> 收入事件快照当时的协议
  -> 按快照协议分账
  -> 生成不可重复的结算凭证
  -> 关键动作写入操作审计日志
  -> 存证、版本、协议、收入、结算进入链上发件箱
```

链上部分的准确表述：

- 已实现 FISCO BCOS 适配器、业务锚定发件箱、失败重试和链上复核接口。
- 已准备并测试 `BusinessAnchor` 合约，支持作品证据、协议、收入事件、结算凭证和审计检查点等业务类型。
- 当前 `app.chain.mode=pending`，页面不会伪造交易哈希，不得宣称“已经完成 FISCO 上链”。

## 2. 产品定位与真实需求

### 2.1 产品是什么

本产品是 AI 创作过程中的“来源档案 + 协作合同 + 结算台账 + 公开核验入口”。

它重点回答五个问题：

1. 这件作品绑定了哪些生成参数和哪个工作流？
2. 当前文件是否与存证时的文件一致？
3. 作品经历了哪些版本，每个版本能否独立复核？
4. 哪些人参与了协作，按什么比例分配，是否本人确认？
5. 某笔收入发生时适用哪一版协议，是否已经结算，能否重复结算？

### 2.2 目标用户、场景和痛点

| 用户 | 典型场景 | 当前痛点 | 本产品提供 |
| --- | --- | --- | --- |
| 独立 AI 创作者 | 商单交付、平台投稿、作品参赛 | 无法说明 prompt、seed、模型和最终文件之间的对应关系 | 自动采集生成参数、文件哈希、来源清单、证书和公开验证页 |
| 2-10 人创作团队 | 多人分工、共同接单、联合投稿 | 分工和分润靠聊天记录，改比例后难以追溯 | 邀请成员、协商比例、逐人确认、协议版本与确认签名 |
| 团队负责人 | 收款后向成员分配收益 | 手工 Excel 易重复、难解释某笔钱按哪版协议分 | 收入事件快照协议、分账流水、结算凭证、防重复结算 |
| 买方或甲方 | 验收 AI 图片或素材 | 收到的文件可能与验收样图不同 | 上传文件后重新计算 SHA-256，并对照公开存证 |
| 评委、平台审核方 | 核验作品来源和协作材料 | 只能相信平台口头说明或截图 | 免登录验证页、机器可读清单、PDF 证书和链上复核状态 |

### 2.3 为什么区块链在这个产品里有作用

区块链不负责判断艺术价值，也不自动决定谁应获得多少比例。它承担四类适合不可篡改记录的职责：

1. 证明某个业务哈希在某个时间点已经存在。
2. 固定协议版本和协议内容哈希，防止事后替换。
3. 固定收入事件和结算凭证，形成可追溯的事件顺序。
4. 让第三方通过合约查询复核业务哈希，而不是只相信平台数据库。

产品采用“链上锚定证据，链下保存业务正文”的方式，避免把原图、完整 prompt、买方信息和密钥直接放到链上。

## 3. 功能边界与非目标

### 3.1 本阶段要做的

- 本地 ComfyUI 生成与参数自动采集。
- 作品文件、生成参数、工作流哈希与创作者签名绑定。
- 来源清单、PDF 存证证书和公开验证。
- 作品版本独立哈希、版本存证、版本演进和当前版本切换。
- 协作邀请、协议协商、比例校验、逐人确认和协议版本历史。
- 授权订单、人工确认收款、收入事件、协议快照、分账和结算凭证。
- 链上发件箱、失败重试、真实回执回填和公开链上复核。
- 关键操作审计留痕。

### 3.2 明确不做

| 非目标 | 原因 |
| --- | --- |
| 通用 AI 绘图平台 | 不与 Midjourney、Stable Diffusion WebUI 或在线生图平台正面竞争；ComfyUI 只是来源采集端 |
| NFT 铸造和交易平台 | 本阶段重点是来源、协作和结算，不引入数字藏品合规风险 |
| 自动判定著作权归属 | 系统证明“谁在何时提交并确认了什么”，不能替代司法或版权登记 |
| 算法强制决定分润比例 | 比例由协作者协商，系统只能提供可编辑建议，最终必须全体确认 |
| 真实银行支付和自动打款 | 比赛阶段采用人工确认收款和业务分账流水，不宣称资金已自动划拨 |
| 模型训练、微调或视频生成 | RTX 4060 8GB 不适合作为这些能力的主线，且会稀释项目定位 |
| Flux 全精度生成 | 8GB 显存无法稳定支持，不能写入已实现能力 |
| 云端模型原始参数存证 | 不同云厂商不保证返回完整工作流、seed 和模型参数，不能作为来源存证的设计前提 |

## 5. 技术架构与责任边界

### 5.1 当前架构

```text
┌───────────────────────────────┐
│ Vue 3 + Vite + Element Plus   │
│ 作品 / 版本 / 协作 / 验证页面 │
└───────────────┬───────────────┘
                │ HTTP API
                ▼
┌───────────────────────────────┐       ┌────────────────────┐
│ Spring Boot 业务后端          │──────▶│ MySQL 业务数据库    │
│ 身份、作品、证据、协议、结算  │       └────────────────────┘
└───────┬───────────────┬───────┘
        │               │
        ▼               ▼
┌──────────────┐  ┌──────────────────────────────┐
│ 文件存储     │  │ chain_anchor 发件箱          │
└──────────────┘  └──────────────┬───────────────┘
                                 │ FISCO SDK
                                 ▼
                     ┌──────────────────────────┐
                     │ FISCO BusinessAnchor      │
                     │ 只保存哈希、类型和时间    │
                     └──────────────────────────┘

┌───────────────────────────────┐
│ 本地 ComfyUI :8188            │
│ 生成 + /history 参数回读      │
└───────────────────────────────┘
```

### 5.2 链上保存什么

| 业务类型 | 链上内容 | 不上链内容 |
| --- | --- | --- |
| `work_evidence` | 作品证据哈希或版本哈希、业务 ID、类型、元数据 URI | 原图、完整 prompt、个人信息 |
| `agreement` | 协议哈希、协议 ID、版本对应元数据 URI | 聊天记录、真实身份材料 |
| `revenue_event` | 收入事件哈希、业务 ID、协议摘要引用 | 买方隐私、银行流水 |
| `settlement_receipt` | 结算凭证哈希、业务 ID、协议版本引用 | 私钥、账户密码 |
| `audit_checkpoint` | 可选审计批次根哈希 | 每条普通操作日志正文 |

### 5.3 权威边界

- **业务数据库**：保存完整业务事实、当前状态和可读正文。
- **本地哈希与签名**：用于复核业务记录是否被改动以及签名人是谁。
- **区块链**：保存某个业务哈希在链上存在过的事实，提供外部时间顺序和公开校验入口。
- **链不可用**：不能阻断上传、协议确认和本地分账；业务记录进入发件箱等待重试。
- **链上成功后**：页面才显示真实交易哈希、区块号和 `onChainVerified=true`。

## 6. 当前配置与运行方式

### 6.1 本地业务模式

当前默认配置：

```yaml
app:
  chain:
    mode: pending
  public-base-url: http://127.0.0.1:5173
```

该模式下：

- 所有业务功能可以完整体验。
- 存证、版本、协议、收入和结算会进入 `chain_anchor`。
- `chain_anchor.chain_status` 保持待上链或失败状态。
- 页面不得显示虚假的 `txHash` 或区块号。

### 6.2 FISCO 模式所需配置

与合作方联调时需要提供或确认：

```yaml
app:
  chain:
    mode: fisco

fisco:
  group-id: 1
  sdk-config-path: ${FISCO_SDK_CONFIG_PATH:}
  private-key: ${FISCO_PRIVATE_KEY:}
  business-anchor-abi: ${FISCO_BUSINESS_ANCHOR_ABI:classpath:abi/BusinessAnchor.abi.json}
  contract:
    business-anchor-address: ${FISCO_BUSINESS_ANCHOR_ADDRESS:}
```

环境变量：

- `FISCO_SDK_CONFIG_PATH`：FISCO SDK 配置文件绝对路径。
- `FISCO_PRIVATE_KEY`：测试或运营账户私钥，只允许放在本地环境变量或密钥系统中。
- `FISCO_BUSINESS_ANCHOR_ADDRESS`：已部署 `BusinessAnchor` 合约地址。
- `FISCO_BUSINESS_ANCHOR_ABI`：可选，默认读取后端 classpath 中的 ABI。

### 6.3 当前公开接口

| 接口 | 用途 |
| --- | --- |
| `GET /api/public/chain-status` | 查看链模式、SDK、私钥、ABI、合约配置和运营地址 |
| `GET /api/public/chain/verify` | 按业务类型、业务 ID 和数据哈希复核发件箱与链上状态 |
| `POST /api/work/evidence/{workId}/anchor/retry` | 作品作者重试存证锚定 |
| `GET /api/public/evidence/{hash}` | 获取公开存证摘要 |
| `GET /api/public/evidence/{hash}/manifest` | 下载来源清单 |
| `GET /api/public/evidence/{hash}/certificate` | 下载 PDF 存证证书 |

## 7. 三阶段开发计划

### 阶段 A：比赛可交付收口（当前阶段，1-3 天）

目标：保证现场能够完整演示，答辩口径一致，不依赖临时开发。

| 工作 | 验收标准 |
| --- | --- |
| 固化演示账号、作品、协议、订单和分账数据 | 按脚本连续走两遍不失败 |
| 录制 ComfyUI 真实生成与自动采集 | 展示 prompt、seed、模型、参数、输出文件和文件哈希 |
| 演示公开验证、来源清单和 PDF 证书 | 未登录浏览器可打开，重新计算哈希一致 |
| 演示版本演进 | 每个版本有独立哈希和链上复核状态 |
| 演示协作与分账 | 多人确认、协议版本、收入快照、重复分账被拒 |
| 演示链上边界 | `pending` 状态清晰，不出现假交易哈希 |
| 准备断网或生成失败兜底 | 使用已存证作品和预录生成片段继续答辩 |

**阶段完成定义：** 本地全流程可复现，录屏、证书、验证页和兜底数据齐全；“链上适配已准备、合作链待接通”表述统一。

### 阶段 B：合作方 FISCO 联调（2-4 天，依赖外部条件）

目标：完成真实联盟链回执闭环。

| 工作 | 验收标准 |
| --- | --- |
| 部署 `BusinessAnchor` 并授权 operator | 运营账户可写入，普通账户写入被拒 |
| 配置 SDK、私钥、群组和合约地址 | `/api/public/chain-status` 显示配置完整 |
| 验证 pending 到 anchored | 交易成功后回填真实 `txHash` 和区块号 |
| 验证链上复核 | `onChainVerified=true`，篡改哈希后为 `false` |
| 验证幂等与失败重试 | 重复锚定不重复写入；链不可用时可重试 |
| 验证协议、收入、结算三类锚定 | 各生成独立链上记录且可查询 |
| 检查敏感数据 | 原图、私人正文和私钥不上链 |

**阶段完成定义：** 至少完成一次“作品证据 -> 协议 -> 收入 -> 结算”全链路真实上链，页面能展示真实交易回执。

### 阶段 C：产品化试点（2-4 周）

目标是形成可给真实团队试用的小范围版本，而不是继续堆演示按钮。

| 优先级 | 能力 | 价值 |
| --- | --- | --- |
| P0 | `generation_job` 后端代理 ComfyUI | 把参数来源从“可信采集器提交”升级为“业务后端实际提交并读取 history” |
| P0 | 用户独立钱包或密钥托管升级 | 从平台代签升级为可证明的用户自持签名 |
| P0 | 接口对象级权限审计 | 防止非参与者读取作品、协议、订单和版本 |
| P1 | 真实支付回调、退款和撤销 | 让收入事件具备支付渠道证据并形成完整订单状态机 |
| P1 | 协议拒绝、反提案和专用状态机 | 提升多方谈判体验，而不是只靠新建协议版本 |
| P1 | 审计日志哈希链与批量锚定 | 降低数据库管理员静默改日志的风险 |
| P2 | 贡献材料登记和比例建议 | 用可解释证据辅助协商，但不由算法直接裁决 |
| P2 | 通知、导出对账单和团队工作台 | 提升真实团队的重复使用效率 |

## 9. 评委常见问题与回答口径

### Q1：这不就是一个 AI 绘图网站吗？

**回答：** 不是。生成只是数据入口，产品真正提供的是生成来源、文件与参数绑定、版本证据、协作协议、收入结算和公开复核。ComfyUI 可以替换，但责任链和结算逻辑保持不变。

### Q2：你怎么证明 prompt 和 seed 真是这张图的？

**回答：** 当前版本由本地采集器提交工作流、读取 ComfyUI 执行历史，并把参数、工作流和输出文件作为一次记录提交；服务端重新计算文件哈希并生成规范化数据哈希。这个说法能证明采集器在本次执行中观察到了这些参数并与文件绑定，但不能夸大成业务后端独立监督了整个模型计算过程。下一阶段会把生成任务迁到后端 `generation_job`。

### Q3：创作者在前端改参数怎么办？

**回答：** 当前采集器从 ComfyUI API 和执行历史取值，不接受手工录入整组参数。服务端仍会验证字段、计算文件哈希和规范化数据哈希。要做到更强保证，需要后端代理 ComfyUI，这一边界已经列入产品化计划。

### Q4：数据库管理员改了数据怎么办？

**回答：** 本地数据库保存业务正文，链上只保存摘要。数据库内容被改后，重新计算的哈希会与已锚定哈希不一致；但只有合作链真实接通并取得回执后，才能提供外部链上证明。当前 pending 模式不会把本地状态冒充链上状态。

### Q5：为什么不用固定 50/50？

**回答：** 固定比例不符合真实协作。不同成员的创意、执行、客户和运营投入可能不同，因此系统让成员自行协商，只做 100% 校验、逐人确认和版本固化。系统可以以后提供建议，但不替成员裁决。

### Q6：有人不同意比例怎么办？

**回答：** 未生效协议不能用于结算。当前可以通过创建新协议版本继续协商，旧协议和确认记录保留；新产品阶段会补充接受、拒绝和反提案专用状态机。

### Q7：先收款后改比例，旧收入按哪版协议？

**回答：** 按收入发生时的协议。确认收款会生成收入事件，并快照 `agreementId`、`agreementHash` 和 `agreementVersion`；分账读取快照，不读取“当前最新协议”。

### Q8：同一订单能不能重复分账？

**回答：** 不能。收入事件状态使用原子条件更新，数据库还有收入事件与分账记录的唯一约束，第二次分账会被业务层明确拒绝。

### Q9：链上分账会把钱打给成员吗？

**回答：** 不会。当前链上锚定的是协议和结算凭证摘要，真实支付和自动转账不在本阶段范围。项目证明分账规则和结果没有被事后替换，不冒充资金托管平台。

### Q10：链挂了系统还能用吗？

**回答：** 可以。业务先落库，锚定记录进入发件箱；链恢复后重试。链失败不会阻断上传、协议确认和本地分账，页面会如实显示待上链或失败。

### Q11：当前真的上链了吗？

**回答：** 当前业务运行在 pending 模式，没有真实交易回执。FISCO 适配器、`BusinessAnchor` 合约、锚定发件箱、重试和复核接口已经准备并通过本地测试，合作方提供链环境和部署地址后即可联调。不会把这一状态说成“已完成上链”。

### Q12：签协议用的签名是用户钱包签名吗？

**回答：** 当前是平台为本地用户生成的托管 RSA 密钥签名，能够证明平台账户下的确认行为，但不是用户独立控制的链上钱包签名。后续需要切换为 FISCO 账户或用户自持密钥。

### Q13：系统会认定版权吗？

**回答：** 不会。系统记录来源、提交时间、文件摘要和成员确认，不替代版权登记或司法裁判。它的价值是降低举证成本，并让协作和收益过程可追溯。

### Q14：你们的差异化在哪里？

**回答：** 很多产品只做“AI 生成”或只给图片加哈希；本项目把作品证据、独立版本、协商协议、收入快照、结算凭证和审计记录连成同一条责任链，并明确区块链只承担可信锚定。

### Q15：商业化从哪来？

**回答：** 优先面向小型 AIGC 工作室和接商单的独立创作者，可按团队席位、存证与证书、协作结算或企业私有部署收费。比赛阶段先验证流程和信任价值，不虚构已有收入。

## 13. 最终完成定义

### 13.1 本次比赛完成标准

满足以下条件即可认为“比赛交付完成”：

1. 观众能理解产品不是绘图工具，而是可信来源和协作结算基础设施。

### 13.2 合作方接通后的完整标准

1. 作品、版本、协议、收入和结算均可获得真实 FISCO 回执。
2. 公开验证页面可从链上合约重新验证数据哈希。
3. 链故障时业务不丢失，恢复后可以补偿锚定。
4. 历史协议和对应历史收入始终按原版本复核。
5. 原图、完整 prompt、个人信息和私钥不上链。
