# 前后端对接指南（给负责前后端的同学）

> 本文档可直接转发。目标：让前端/后端在不读合约源码的情况下，把整个产品串起来跑通。

## 一、部署与地址

```bash
npm install
npx hardhat compile
npx hardhat test                          # 10 项测试，全绿
npx hardhat run scripts/deploy.js         # 本地链部署，地址写入 deployments/
npx hardhat run scripts/demo-e2e.js       # 全链路演示（答辩录屏用）
```

部署产物（本地节点）：

| 合约 | 说明 |
|---|---|
| `AICreationEvidence` | 存证 + 角色 + 状态机 + 纠纷 |
| `AICreationProfitSplit` | 贡献量化 + 收益托管 + 分润 |

**部署完必须执行一次**：`evidence.setSettler(splitAddress, true)`。否则首次结算后作品状态不会自动变成"已结算"（资金不受影响，但概览页会显示错误状态）。

ABI 在 `artifacts/contracts/*.sol/*.json`，前端直接 import 里面的 `abi` 字段。

## 二、哈希口径（最容易踩的坑）

链上只认 `bytes32`，同一份内容用不同方式算哈希，校验就永远失败。统一用 `scripts/hash-utils.js`：

```js
const { hashText, hashJson, hashFile } = require("../scripts/hash-utils");

hashText("赛博朋克风格的黑猫...")     // 提示词
hashJson({ title, model, scene })      // 元数据 / 评分明细（内部递归排序 key）
hashFile("./output/cat.png")           // 图片 / 视频 / 压缩包
```

规则：
- 文本 → `keccak256(utf8)`
- JSON → **先递归排序 key** 再 `keccak256(utf8)`（不排序，同样的对象会得到不同哈希）
- 文件 → `keccak256(文件二进制)`
- 全系统只用一种算法；要接老系统用 SHA-256 也行，但别混用

## 三、完整调用顺序（前端一次创作流程）

### 1. 开始创作 → 建作品

```js
// 用户输入提示词后立刻上链，这是"输入层"锚点
const inputRoot = hashText(promptText);
const tx = await evidence.createWork(inputRoot, "ipfs://meta/xxx.json");
const workId = (await evidence.totalWorks());   // 你的作品编号
```

`createWork` 内部会自动写入第 1 条 `Prompt` 证据，并把创作者登记为「创意发起者」。

### 2. 邀请协作者

```js
// role: 1 创意发起 / 2 提示词设计 / 3 模型方 / 4 生成执行 / 5 后期编辑 / 6 运营推广
await evidence.addContributor(workId, otherAddress, 2);
```

对方登录后必须自己确认，**这是"防止被挂名分钱"的关键**：

```js
await evidence.connect(otherSigner).acceptRole(workId);
```

### 3. 创作过程中持续追加证据

```js
// etype: 0 提示词 / 1 参数 / 2 生成结果 / 3 人工编辑  （4 最终成品只能通过 finalizeWork）
await evidence.addEvidence(workId, 3, hashFile("./v2.png"), "ipfs://ev/v2.png");
```

建议采集时机：
| 用户动作 | etype |
|---|---|
| 修改提示词 | 0 |
| 调整 cfg / steps / seed / 采样器 | 1 |
| 点击生成、拿到图 | 2 |
| 局部重绘、调色、导出 | 3 |

### 4. 定稿

```js
await evidence.finalizeWork(workId, hashFile("./final-4k.png"), "ipfs://ev/final.png");
```

定稿后证据链封闭（不能再追加），状态变为 `Finalized`，此时才能进入分润。

### 5. 生成评分 → 上链

后端调用评分引擎（`scripts/scoring-engine.js`），它输出合约直接可用的七项指标：

```js
const { scoreWork } = require("../scripts/scoring-engine");
const { scores, sheetHash } = scoreWork(evidenceRecords, contributors, {
  adoption: { [addr]: { versions: 2, adopted: 2, isFinal: true } },
  salesCount: { [operatorAddr]: 12 }
});

await profitSplit.lockShares(workId, scores, sheetHash);   // 仅 scorer/admin 可调
```

把 `sheet`（含每项分数的计算依据）存数据库或 IPFS —— 事后任何人可以用它复算，`hashJson(sheet)` 必须等于 `sheetHash`。

### 6. 收益进账（托管）

```js
await profitSplit.depositRevenue(workId, { value: ethers.parseEther("0.3") });
```

任何人可付款；作品处于纠纷冻结时**依然能收款**（钱进托管，不丢），只是暂时不能结算。

### 7. 结算（任何人可触发）

```js
await profitSplit.settle(workId);   // 无参数，权限开放
```

条件：份额表已锁定 + 无待处理异议 + （全员确认 或 3 天异议期已过）。

### 8. 提现

```js
const pending = await profitSplit.pendingWithdrawals(userAddress);  // 展示"可提取"
await profitSplit.withdraw();                                       // 或 withdrawTo(冷钱包)
```

采用 Pull 模式：结算只记账，用户自己来领，避免某个地址转账失败导致整批回滚。

### 9. 纠纷

```js
await evidence.connect(user).raiseDispute(workId, "第二轮分成与约定不符"); // 协作者/平台
await evidence.connect(arbiter).resolveDispute(workId, 1);                 // 1=Finalized 解除, 4=Revoked 作废
await profitSplit.connect(user).objectShares(workId, "我的迭代被低估");    // 异议期内的份额异议
await profitSplit.connect(arbiter).resolveObjection(workId, true);         // true=驳回异议
```

## 四、时间线视图（前端画证据链用）

```js
const ids = await evidence.getWorkEvidenceIds(workId, 0, 50);
for (const id of ids) {
  const e = await evidence.getEvidence(id);   // { dataHash, prevChainHash, chainHash, operator, timestamp, etype, role, uri }
}
const [ok, badIndex] = await evidence.verifyChain(workId);  // 一键验真
```

`chainHash` 建议在 UI 上展示前 10 位 + 复制完整值，视觉上体现"链式"。

## 五、事件（后端 indexer 用）

| 事件 | 触发 | 关键字段 |
|---|---|---|
| `WorkCreated` | createWork | workId, creator, inputRoot |
| `ContributorAdded` / `ContributorAccepted` | 角色登记/确认 | workId, account, role |
| `EvidenceAppended` | 每条证据 | workId, evidenceId, etype, operator, chainHash, uri |
| `WorkFinalized` | 定稿 | workId, resultHash, processRoot |
| `WorkStatusChanged` | 状态机流转 | workId, oldStatus, newStatus |
| `SharesLocked` | 份额上链 | workId, version, accounts[], ci[], totalCi |
| `RevenueDeposited` | 收益入托管 | workId, payer, amount, escrow |
| `RevenueSettled` | 结算 | workId, round, gross, platformFee, net |
| `ShareCredited` | 每人分到多少 | workId, account, ci, amount |
| `Withdrawn` | 提现 | account, amount |
| `DisputeRaised` / `DisputeResolved` | 纠纷 | workId, reason / outcome |
| `SharesObjected` / `ObjectionResolved` | 份额异议 | workId, account / dismissed |

## 七、常见 revert 原因

| 错误 | 原因 | 处理 |
|---|---|---|
| `InvalidStatus` | 作品不是 Draft 却继续写证据；或未定稿就锁份额 | 检查状态机 |
| `NotContributor` | 未登记就想写证据 | 先 addContributor |
| `RoleNotAccepted` | 被登记但没 acceptRole | 让对方确认 |
| `NotScorer` | 非评分方调 lockShares | 用 admin 或 setScorer 指定地址 |
| `NotListedContributor` | 评分表里出现非协作者 | 只传已确认的协作者 |
| `ZeroTotalContribution` | 所有 CI 都为 0 | 检查评分输入 |
| `ObjectionWindowOpen` | 异议期未过且未全员确认 | 等 3 天或催全员 consentShares |
| `ObjectionPending` | 有未处理异议 | 仲裁 resolveObjection |
| `NothingToSettle` | 托管余额为 0 | 先 depositRevenue |
| `InvalidWorkStatus` | 作品被冻结/作废 | 先 resolveDispute |
| `NotAdmin` / `NotArbiter` | 权限不足 | 换账号 |
