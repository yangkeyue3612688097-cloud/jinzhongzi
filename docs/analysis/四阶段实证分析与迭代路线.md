# 四阶段实证分析与迭代路线

> 分析基准：friend-project 仓库全量代码（8 Controller / 1 Interceptor / 11 Service / 9 ServiceImpl / 17 实体 / 17 建表语句 / 10 Vue 页面 / BusinessAnchor.sol 及未启用合约线），检索顺序 controller → interceptor → service → 实体 → SQL → 前端 → 配置/合约。每条结论均附文件路径，无代码支撑处标注【暂无代码实现】。

## 阶段一 用户定位与需求梳理

### 1. 使用者类型判定（以四层齐全——接口+服务+数据表+页面——为"可服务"标准）

| 类型 | 判定 | 依据 |
|---|---|---|
| **个人 AI 创作者** | ✅ 可服务 | `AiWorkController`（create/import/list/detail/generation/evidence 共 9 端点）+ `AiWorkGeneration` 实体含 prompt/modelName/modelVersion/seed/steps/cfgScale/sampler/workflowHash 等 11 个参数字段 + `LocalGenerate.vue` 页面。画像：本地用 SD/ComfyUI 出图的学生/独立设计师；痛点：生成参数散落本地易丢、作品被搬运后无法自证创作过程 |
| **2–5 人小微协作团队** | ✅ 可服务 | `CollaborationController` + `CollaborationInviteController` + `CollaborationAgreementController` + 协作域 7 张表。画像：接单小团队（主创+画师+后期）；痛点：分成靠口头约定、改比例时旧账被重算、确认无留痕、分账对不上账 |
| **买家 / 公众验证方** | ✅ 可服务 | `PublicEvidenceController` 5 个免登录端点（`/public/evidence/{dataHash}`、`/chain-status`、`/chain/verify`、`/manifest`、`/certificate`），`/public/**` 在 `WebMvcConfig` 拦截白名单内，`Verify.vue` 路由无 `requiresAuth`。画像：拿到作品的人；痛点：无法判断作品来源真伪 |
| **企业** | ❌【暂无代码实现】 | `User` 实体无 role/tenant 字段，`JwtInterceptor` 只认证不鉴权，无组织/多租户概念 |
| **学生 / 赛事机构** | ❌【暂无代码实现】 | 全仓库 0 处 competition/赛事 代码 |
| **监管 / 司法机构** | ❌【暂无代码实现】 | 无可信时间戳、公证、司法采信链任一环节；无对监管的任何接口 |

### 2. 需求层级拆分（Kano 模型）

**刚需（基本型，缺一则业务不成立）**
1. 账号注册登录与身份认证 — `UserController.register/login`，`JwtInterceptor`
2. 生成过程参数自动留存 — `/api/works/import/comfyui` + `ai_work_generation` 表
3. 存证生成与防篡改哈希 — `EvidenceServiceImpl`（SHA-256 + 平台签名验签）
4. 存证上链锚定（含失败重试）— `BusinessAnchorService` + `chain_anchor` 表 + `/anchor/retry`
5. 协作协议版本化与逐人确认 — `collaboration_agreement`（多版本）+ `collaboration_agreement_confirmation`
6. 收款→按约分账→凭证留痕 — `RevenueEvent`→`ProfitRecord`→`SettlementReceipt`
7. 免登录公开验真 — `PublicEvidenceController` + `Verify.vue`

**期望型（有则满意度显著提升）**
- 作品版本历史与确认 — `WorkVersionController` + `VersionHistory.vue`
- 协作邀请流转 — `CollaborationInviteController` + `Invites.vue`
- 数据看板 — `StatisticsController` + `Home.vue`
- 存证证书 / 数据清单 — `/certificate`、`/manifest`
- 锚定失败手动重试 — `/evidence/{workId}/anchor/retry`

**兴奋型（超出预期，演示亮点）**
- 链上实时校验通过/拒绝 — **当前实际不可用**（见阶段四问题 1/2），修复后才成立
- 模型指纹校验 — 【暂无代码实现，后端 0 处引用】
- 合约自动分润 — 合约 `AICreationProfitSplit.sol` 已写并有 11 项测试，但平台主线仅调 `BusinessAnchor.anchor`，【已交付、未集成】

## 阶段四 现存问题与改进

1. **链上验真双断点（最严重）**：① `EvmEvidenceChainGateway.verify()` 与 `BusinessAnchor.sol` 的 `verify(bytes32,bytes32,bytes32)` 签名不一致 → 调用必 revert；② `verificationAvailable` 仅 fisco 模式为真，evm 模式直接走数据库分支。**改进**：合约侧改 4 参或网关侧改 3 参（后者 1 行）；判断条件改为 `mode != pending`；补一条集成测试：锚定→链上 verify 通过→改 1 字节→verify 失败。
2. **`update-wallet` 静默不生效但仍返回 success**：`UserController.java:83-91` 日志写"人工绑定申请未生效"，接口却 `Result.success()`。用户以为绑定成功。**改进**：返回明确文案"当前为平台托管模式，绑定申请已记录待审核"，前端弹窗提示；或直接下线该端点。
3. **协议确认只签不验**：签名写入 `collaboration_agreement_confirmation` 后无任何校验路径。**改进**：确认时服务端即时 `signingService.verify`，失败拒绝确认；公开验真接口增加"协议签名可验证"字段。
4. **业务级越权未系统审计**：`JwtInterceptor` 只做认证（解析 userId），授权完全依赖各 Service 自查。`/distribute`、`/order/confirm`、协议反提案等敏感操作需逐一核对发起人身份校验；无则补 `collaborator` 角色判断。
5. **单一 operator 明文私钥**：`application-local.yml` 使用 Hardhat 账户 #0 私钥，所有链上交易同一主体——"平台托管签名"是如实设计，但私钥入库有泄露风险。**改进**：至少改环境变量注入 + .gitignore 外置；BP 中如实表述为托管模式。
6. **主线合约无时序哈希链**：`BusinessAnchor.sol` 仅独立锚定 + latestAnchorId，无 prevHash；`Evidence` 表亦无链式字段。申请书主打"时序哈希链"只存在于未启用的 `AICreationEvidence.sol`。**改进**：要么把 `AICreationEvidence.sol` 接入主线（含 prevChainHash 校验演示"改一步全链失效"），要么申报口径改为"逐事件独立锚定"。
7. **贡献量化空壳**：`contribution` 表无分值/比例字段、无写入代码 →【暂无代码实现，属于设想】。BP 中不得出现"贡献度自动量化"；如要实现，最小路径是协议确认与收款时写事件级贡献记录，配合已写好的 `ContributionMath.sol`。
8. **pending 模式语义诚实但可见性差**：不写 tx_hash、失败记 STATUS_FAILED+retry_count 是亮点，但前端无失败列表与重试入口聚合页。**改进**：锚定失败在 `WorkDetail.vue` 顶栏红条提示 + 一键重试。
9. **无自动重试调度**：outbox 只有手动重试端点。**改进**：`@Scheduled` 扫 retry_count<3 且 STATUS_FAILED 的记录重发。
10. **证书为数据接口非文件**：`/certificate` 返回 JSON。**改进**：服务端渲染 PDF（含哈希、区块号、时间、验真二维码），演示与传播价值远高于 JSON。

## 版本迭代路线

**v1 稳定最小可用（当前 → 2 周）**
- 修复链上验真双断点（问题 1）＋协议确认验签（问题 3）
- update-wallet 文案修正（问题 2）、敏感操作越权审计（问题 4）
- 私钥外置环境变量（问题 5）
- 一键部署脚本 + 部署文档；3 个真实创作者试用记录
- 口径统一：删除"贡献度自动量化/时序哈希链（主线）"表述

**v2 完善体验（+4 周）**
- 集成 `AICreationProfitSplit.sol`：链上分润指令 + 链下打款回执上链
- 模型指纹接入导入链路；证书 PDF + 二维码
- 锚定自动重试、消息通知、失败可视化
- 贡献事件记录入口（contribution 表启用，事件级而非自动量化）

**v3 拓展增值（3 个月后）**
- `AICreationEvidence.sol` 时序哈希链接入（或等效链式锚定），演示"篡改定位到步"
- FISCO BCOS 国产链实测；挑战期/仲裁机制（合约侧能力迁移）
- 按结算流水抽佣的商业化计量；企业租户（届时才具备承接条件）

## 区分：真正服务业务的技术 vs 堆砌部分

**服务业务**：Merkle/哈希存证（自证创作过程）、outbox 锚定（低成本可复核）、协议版本化+逐人确认（防旧账重算）、CAS 原子分账（防重复结算）、免登录验真（买家信任入口）。

**堆砌/未接线**：时序哈希链（仅未启用合约）、`ContributionMath.sol` 与贡献量化（0 调用）、模型指纹（0 引用）、FISCO 网关（本机无节点）、自持私钥叙事（实际托管）、司法/监管对接（0 代码）。

## 申报书可用文字

> 本项目面向 AI 内容创作者个人与 2–5 人小微协作团队，聚焦当前 AI 创作生态中的两大痛点：其一，作品创作过程参数（提示词、模型版本、随机种子等）随本地文件流失，作品被搬运或权属争议发生时缺乏可验证的过程证据；其二，多人协作的收益分配依赖口头约定，比例变更无留痕、分账执行无凭据，纠纷频发且难以举证。系统以"过程存证—协作确认—按约分账"为主线：创作参数经哈希与签名固定后锚定上链，形成不可篡改的存证记录；协作协议支持多版本管理与逐人确认，确保各方对分成规则的认可有据可查；收款发生后系统按生效协议原子化分账，出具含链上锚定信息的结算凭证，任何第三方均可凭哈希免登录核验。系统将区块链用于证据固定与规则执行两个真实环节，为 AI 创作确权与协作分配提供了可落地的技术方案。

（如实边界，建议随文注明：当前版本采用平台托管签名与本地测试链，链上验真与合约分润处于集成阶段；暂不具备服务企业客户与监管机构的能力。）
