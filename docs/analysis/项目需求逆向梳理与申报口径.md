> 方法：对 `friend-project`（后端 8 个 Controller / 17 张表 / 前端 10 个页面）+ `ai-evidence-chain`（5 个合约）+ `model-fingerprint`（独立工具）做逐文件走查。

## 一、用户定位：这个系统实际是给谁用的

### 1.1 有完整代码支撑的用户

| 人群 | 代码支撑 | 他们的痛点 | 结论 |
|---|---|---|---|
| **AI 创作者（个人）** | 前端全部 10 个页面均为此视角：上传 `WorkUpload.vue`、本地生成 `LocalGenerate.vue`、作品详情 `WorkDetail.vue`、版本历史 `VersionHistory.vue`、个人中心 `Profile.vue` | ①"作品是我做的"无凭证，生成参数（提示词/模型/种子）存本地易丢易改；②被盗用、被二次售卖时举证困难 | ✅ 核心用户 |
| **小微协作团队（2–5 人）** | 协作域 6 张表 + 4 个 Controller：`collaboration`、`collaboration_invite`、`collaborator`、`collaboration_agreement`、`collaboration_agreement_confirmation`、`contribution` | 分成比例靠口头约定；改比例时旧账被一起重算；成员确认过程无留痕 | ✅ 核心用户 |
| **买家 / 公众（验证方）** | `PublicEvidenceController`（`/public/evidence/{hash}`、`/public/chain/verify`、`/public/evidence/{hash}/manifest`、`/public/evidence/{hash}/certificate`），**免登录**；前端 `Verify.vue` 公开页 | 看到一张 AI 图，无法判断创作过程是否真实、有没有被篡改 | ✅ 有真实接口，但仅"查询"，无账号体系 |

### 1.2 有部分支撑、但不足以宣称服务的人群

| 人群 | 实际支撑 | 不能宣称的部分 |
|---|---|---|
| **平台运营方** | `/statistics/dashboard` 一个聚合接口 + `operation_log` 表（仅记录改密码、钱包、身份签名、头像 4 类操作） | ❌ 无管理后台、无审核队列、无风控、无完整审计（操作日志覆盖面很窄） |
| **监管 / 司法机构** | 仅"公开可查验"：任何人都能按哈希查证据与链上状态 | ❌ 无监管系统对接、无司法出证流程、无取证授权机制 —— **仅为设想** |

### 1.3 当前版本无法服务的人群（不要写进申报书）

| 人群 | 原因（代码事实） |
|---|---|
| **企业客户** | 无组织架构、无角色权限体系（`User` 表只有 `id/username/password/email/avatar/...`，没有 role、没有 tenant_id）、无私有化部署方案、无 SLA |
| **学生 / 赛事机构** | ⚠️ 更正：仓库里 `upgrade_20261030_competition.sql` 文件名虽含 "competition"，但内容是**"比赛闭环升级"**（给 user 加签名身份字段、给 profit_record 加 order_id、给 work_version 加 version_hash 等 ALTER 语句），**不是赛事业务模块**。系统里没有任何赛事/评审/作品提交打分功能 —— 服务赛事用户为**设想** |
| **大型 MCN / 版权代理机构** | 无批量授权、无版权登记对接、无合同模板管理 |

## 二、原始业务需求：刚需 vs 凑技术点

### 2.1 刚需（有端到端代码闭环，页面→数据库→链上）

|---|---|---|
| **创作过程存证** | `LocalGenerate.vue` 浏览器直连本机 ComfyUI(127.0.0.1:8188) → 回读真实执行参数 → `EvidenceServiceImpl` 写 `evidence` + `ai_work_generation` → outbox `chain_anchor` → 链上锚定 | ✅ 完整（实测上链成功，区块 5） |
| **存证人对数据签名 + 验签** | `EvidenceServiceImpl:104` `signingService.sign(creator.getPrivateKeyEnc(), dataHash)`；`:228` `signingService.verify(...)` → `signatureVerified` 返回前端 | ✅ 签发与验签都有（但私钥为平台托管，见 4.2） |

## 三、核心 / 次要 / 伪需求

### ✅ 核心（没有它项目就不成立）

1. **创作过程存证**：生成参数 + 作品哈希入库并锚定上链，可回溯到"用什么模型、什么提示词、什么种子"
2. **存证签名与验签**：证明"这条存证是该创作者提交的"
3. **协作协议版本化确权**：逐人确认、版本快照、改比例不追溯
4. **收入分账 + 结算凭证**：按确认比例分、凭证上链、防重复
5. **公开免登录验真**：买家/公众凭哈希自查

### 📌 次要（锦上添花，缺了不影响主流程）

1. 作品版本历史对比展示（`WorkVersion` + `VersionHistory.vue`，存在但信息展示偏简单）
2. 数据看板（1 个聚合接口）
3. 存证证书下载（`/certificate` 接口存在）
4. 操作日志（`operation_log` 仅 4 类操作，覆盖面窄，属"有比没有好"）
5. 模型指纹工具（已做，待集成）
6. 合约自动分润能力（已做，待集成）

### ❌ 伪需求 / 为堆技术点而加（申报书别提，或降级表述）

| 伪需求 | 判断依据 |
|---|---|
| **"链上自动计算贡献比例作为平台主流程"** | 真实协作里比例是**协商**出来的（她的协议域就是这么设计的）。CI 公式自动定比例更像"辅助评分"，若当成主流程，用户不会接受"合约替我定分成" |
| **"去中心化存储作品原文"** | ❌ 代码里没有任何 IPFS/Arweave/内容寻址存储，文件存本地磁盘（`upload-path: C:/.../uploads/`），链上只有 32 字节哈希。**不能写"去中心化存储"** |
| **"AI 生成内容合规审查/深度伪造检测"** | ❌ 全仓库 0 行相关代码。若旧材料提过，建议删除 |
| **"多链/跨链互操作"** | ❌ 只有单条 EVM 链（本地 Hardhat）+ 一套未接通的 FISCO 网关代码。**不能写跨链** |
| **"版权登记/司法出证"** | ❌ 无版权局对接、无司法链、无出证流程。只有"可查验" |
| **"区块链浏览器级全节点部署"** | ❌ 只有本地开发链，无生产节点、无共识治理 |

## 四、代码没有实现 / 与常见宣传不符的地方（必须如实标注）

### 4.1 完全未实现（仅为设想）

1. **企业级多租户与权限体系**：`user` 表无 role/tenant 字段，无 Spring Security 角色控制 → 仅为设想，当前版本无法服务企业
2. **监管/司法对接**：无任何对接代码 → 仅为设想
3. **赛事/评审业务**：无赛事表、无接口、无页面 → 仅为设想（"competition" 那个 SQL 是比赛用的字段升级，不是赛事功能）
4. **去中心化存储**：文件存本地磁盘 → 仅为设想
5. **内容合规审查 / AI 检测**：0 行代码 → 仅为设想
6. **跨链**：无 → 仅为设想

### 4.2 已实现但与"理想叙事"有差距（答辩要收着说）

1. **身份是"平台托管"，不是"用户自持私钥"**
   `UserServiceImpl.attestIdentity` 用 `user.getPrivateKeyEnc()`（私钥加密存库）调 `signingService.sign`，即**平台代签**。`update-wallet` 接口的日志文案直接写明"钱包地址已改为平台托管身份，人工绑定申请未生效"。
   → 可以说"平台托管签名身份"，**不能说"用户自主掌控私钥/去中心化身份"**。

2. **协议确认签名只写不验**
   `CollaborationAgreementServiceImpl:428` 写入 `confirmation.signature`，但全仓库**没有对协议确认签名的验签调用**（存证侧有验签，协议侧没有）。
   → 可以说"确认过程留痕并签名"，**不能说"协议签名可独立验证"**（要补验签才行，工作量不大）。

3. **智能合约分润与平台业务是两条线**
   平台走"协商比例 + 凭证锚定"；合约走"CI 自动比例 + 托管分钱"。二者**未打通**。
   → 可以说"两条技术路线均已实现并验证"，**不能说"平台已由合约自动分账"**。

4. **锚定是异步 outbox**
   `chain_anchor` 表 + 重试机制，交易提交后不立即生效（P2/P3 设计如此）。对外说"上链"时，应表述为"异步锚定、失败可重试、不伪造交易哈希"。

5. **链是内存链，重启即清空**
   Hardhat 本地节点数据在内存，重启后历史交易查不到（数据库记录仍在）。演示前需重走流程；**不能声称"链上数据永久保存"**（生产需换持久化节点）。

## 五、申报书可直接使用的一段话

> **项目面向谁、解决什么痛点（主推荐版本）**
>
> 本项目面向 AI 创作者个人及小微协作团队，聚焦 AI 创作领域"确权难、分成易纠纷、来源不可验证"三大痛点。系统采用"业务平台做体验、区块链做可信锚定"的架构：创作者完成作品上传或本地 AI 生成时，提示词、模型、种子等真实生成参数与作品哈希一并签名存证并锚定上链，形成不可篡改的创作过程证据链；多人协作时，分成比例经全体成员逐人确认后版本化固化，调整比例不追溯历史账目；作品授权收入按确认比例自动分账，并生成可公开核验的结算凭证。买家、平台及任何第三方均可通过免登录验证入口，凭哈希查验存证真伪与链上状态，从机制上回答"这件 AI 作品是谁做的、怎么做的、收益怎么分"。

**短版（用于摘要或 PPT 首页，80 字内）**

> 面向 AI 创作者与小微协作团队的可信存证与分润系统：生成过程签名上链、协作比例逐人确认且版本化、收益按约分账并出具可公开核验的凭证，解决 AI 作品"确权难、分账乱、验真难"。

## 六、答辩口径速查（被追问时按这张表回答）

| 评委可能问 | 安全回答 | 不要说的话 |
|---|---|---|
| 链上到底存了什么？ | 只存 32 字节哈希与业务标识，原文在数据库和文件系统 | "作品存在链上" |
| 谁在签名？ | 平台托管签名身份，存证与确认由系统代签并留痕 | "用户自己管私钥" |
| 分账是合约自动执行吗？ | 平台按协商比例分账并上链存证；合约自动分润能力已实现，处于待集成阶段 | "合约自动打钱给创作者" |
| 能服务企业吗？ | 当前是面向创作者的工具型产品，企业版需要权限与租户体系，属后续规划 | "已支持企业级部署" |
| 和普通存证平台的区别？ | 存的是**生成过程参数**（模型/提示词/种子）+ 协作协议版本 + 分账凭证，不是单纯文件哈希 | "我们也能做版权登记" |
| 链挂了业务会怎样？ | 业务不阻塞，锚定进 outbox 重试，状态可查、不伪造哈希 | "链上链下强一致" |
