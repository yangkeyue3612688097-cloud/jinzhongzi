## 0. 一页结论

**这个项目是什么：**
面向 AI 创作者与小型创作团队的可验证生成来源、协作确权与收益分账平台。

**一句话承诺：**
AI 作品从生成、存证、协作到分账，每一步都能校验。

**当前的准确状态：**
业务闭环已经在本地跑通（生成参数采集 → 文件哈希 → 创作者签名 → 来源清单/证书 → 公开验证 → 版本 → 协作协议 → 授权订单 → 收款事件 → 协议分账 → 审计留痕），
链上部分处于 **pending 模式**，只预留了适配接口，没有任何真实链上交易。

**答辩口径（必须统一）：**
说"存证数据已按链上写入格式准备好，合约由合作方承接"，不说"已经上链"。

## 1. 产品定位

### 1.1 定位陈述

> 给 AI 创作者和 2-10 人创作小组用的"作品来源档案 + 协作合同 + 分账台账"。
> 它不负责把图做得更好看，负责的是：这张图是谁、用什么参数、在什么时候生成的，
> 后来有没有被换过，几个人怎么约定分钱，钱按约定分到位没有。

### 1.2 为什么这个定位成立

AI 图片的稀缺性不在"能生成"，而在"能自证"。三个现实问题：

1. **来源说不清。** 买家或平台看到一张图，无法判断它是 AI 生成、二次修改还是直接搬运；即使作者报了 prompt，也无法证明这个 prompt 真的对应这个文件。
2. **协作说不清。** 多人协作时口头约定"我 60 你 40"，没有可核验的协议快照，事后任何一方都能改口。
3. **收益说不清。** 收了多少钱、按什么比例分、分给谁、分了几次，全在 Excel 或聊天记录里。

这三件事恰好都能用"哈希 + 签名 + 不可变事件序列"表达，也正是区块链擅长承接的部分。所以项目的技术选型是业务驱动的，不是为了用链而用链。

### 1.3 明确不做什么（防止定位漂移）

| 不做 | 原因 |
| --- | --- |
| 通用 AI 绘图工具 | 与 MJ/SD 正面竞争，无优势，且会稀释"存证"主线 |
| NFT 铸造/交易平台 | 法律与合规风险高，与比赛主题（可信数据）不符 |
| 自动判定著作权归属 | 平台只能证明"谁在什么时间提交了什么"，不能替代司法确权 |
| 自动推断贡献比例 | 贡献度是人的协商结果，系统只负责固化和执行 |
| 真实支付通道 | 比赛阶段用"人工确认收款 + 订单状态机"表达，商业化阶段再接支付回调 |
| Flux 全精度 / 视频生成 / 模型微调 | RTX 4060 8GB 显存跑不动，写进方案就是给自己挖坑 |

### 1.4 目标用户与真实痛点

| 用户 | 典型场景 | 现在怎么解决 | 痛点 | 本产品给什么 |
| --- | --- | --- | --- | --- |
| 独立 AI 创作者 | 接商单、投稿、参加征集 | 发原图 + 口头说明 | 无法证明原创，被质疑"AI 拼的"时没有证据 | 可下载的来源清单 + 二维码证书 + 公开验证页 |
| 小型 AIGC 工作室（2-10 人） | 多人分工出图、共同接单 | 微信群口头分账 | 比例靠记忆，结算靠截图，容易扯皮 | 协议起草 → 双方确认 → 比例锁定 → 按协议分账 |
| 买方 / 甲方 | 采购 AI 素材 | 看样图，签纸质合同 | 拿到手无法确认与样图一致 | 用文件哈希核对交付物是否被替换 |
| 评审 / 平台审核 | 核验提交材料 | 人工比对 | 无法快速判断材料真伪 | 免登录 `/verify/:hash` 一页看完 |

### 1.5 需求分层

**Must（没有就不是这个产品）**
- 生成参数与输出文件的强绑定
- 文件哈希 + 创作者签名 + 可公开复核
- 多人协议的比例固化与确认留痕
- 收益事件驱动分账，且不可重复

**Should（决定比赛名次）**
- 版本演进与篡改发现
- 一键导出 PDF 存证证书
- 完整操作审计链
- 生成过程由后端观测（而非前端自报）

**Could（商业化再谈）**
- 真实支付回调与对账
- 贡献度登记与加权分配
- 链上结算凭证与链上查询
- 侵权投诉与撤销流程

## 2. 需求澄清：概念与角色边界

这一节是给评委和合作方看的"防误解说明"，也是后续开发的约束。

### 2.1 六个必须澄清的概念

| 说法 | 准确含义 | 不能宣称 |
| --- | --- | --- |
| 存证 | 平台在某一时刻记录了文件哈希、生成参数、操作者签名，并生成可复核的数据包 | 不等于著作权登记，不等于司法认定 |
| 时间戳 | 平台数据库记录时间 | 不是第三方可信时间戳（TSA），上链后才是链上时间 |
| 生成来源 | 当前由前端采集 ComfyUI 返回的参数后提交 | 尚未做到"后端亲自观测生成过程" |
| 贡献度 | 协作者对作品的投入程度 | 系统不自动计算，`collaborator.contributed_amount` 是累计分账金额，不是贡献度 |
| 确认收款 | 运营/创作者在后台点击确认 | 没有银行流水或支付回调佐证 |
| 分账 | 本地业务流水，按已确认协议比例生成 `profit_record` | 不是链上转账，不是真实资金划拨 |

### 2.2 角色与权限

| 角色 | 能做什么 | 不能做什么 |
| --- | --- | --- |
| 创作者（作品所有者） | 生成/上传作品、发起存证、创建版本、邀请协作者、起草协议、创建订单、确认收款、触发分账、导出证书 | 不能单方面修改已确认的协议比例 |
| 协作者 | 接受邀请、确认协议、查看自己参与的作品与分账 | 不能替他人确认，不能修改协议条款 |
| 买方 | 下单、查看授权作品与凭证 | 不能看到未授权作品 |
| 公众 / 评审 | 通过 `/verify/:hash` 查看存证摘要、下载清单、校验文件 | 无需登录，也看不到隐私字段 |
| 平台运营 | 审计日志查询、异常处理 | 不应能伪造签名 |
| 链（合作方 FISCO） | 承接存证锚定、规则公示、结算凭证 | 不存原图，不存个人信息 |

### 2.3 端到端主流程（5 条）

**流程 A：生成 → 存证 → 公开验证**
```
本地 ComfyUI 出图
  → 采集 prompt/negative/model/seed/steps/CFG/size/sampler + 工作流哈希
  → 上传图片，服务端算 SHA-256
  → 规范化 JSON → dataHash
  → 创作者私钥签名
  → 生成 provenance_manifest.json + PDF 证书（含二维码）
  → 任何人访问 /verify/:hash 复核
```

**流程 B：版本演进**
```
作品 v1 存证 → 上传 v2 → 独立文件哈希与版本哈希
  → 设为当前版本 → 详情页看到版本链 → 任一版本可单独复核
```

**流程 C：协作确权**
```
主账号邀请协作者 → 对方接受 → 起草协议（比例合计 100%）
  → 各方逐一确认 → 协议哈希 + 各自签名固化
```

**流程 D：订单 → 收款 → 分账**
```
创建授权订单（作品、买方、金额）
  → 确认收款 → 生成唯一 revenue_event
  → 按已确认协议比例分账 → 写 profit_record
  → 同一订单再次分账被拒绝
```

**流程 E：审计回溯**
```
存证/协议/订单/收款/分账/版本 等关键动作 → operation_log
  → 按用户/时间查询 → 形成可展示的操作时间线
```

## 4. 技术方案

### 4.1 现状架构

```
┌──────────────────────────────┐
│ Vue 3 + Vite + Element Plus  │
│  :5173                       │
└───────┬──────────────┬───────┘
        │ /api         │ /comfy（Vite 代理，直连）
        ▼              ▼
┌───────────────┐  ┌──────────────────┐
│ Spring Boot   │  │ 本地 ComfyUI     │
│  :8080        │  │  :8188 (CPU/GPU) │
│ MyBatis-Plus  │  └──────────────────┘
└───┬───────┬───┘
    │       │
    ▼       ▼
 MySQL   uploads/ + outputs/
    │
    ▼
EvidenceChainGateway
    └── PendingEvidenceChainGateway（未上链）
```

问题：前端直连 ComfyUI，意味着"参数是客户端说的"。评委只要问一句"你怎么保证前端没改参数"，现有链路就答不上来。

### 4.2 目标架构（P1 完成后）

```
Vue 前端 ──/api──▶ Spring Boot ──HTTP──▶ ComfyUI :8188
                        │
                        ├── generation_job（本次生成的事实记录）
                        ├── 下载输出 → SHA-256 → 存证 → 签名
                        ├── 自动创建作品 + 版本 + 证据
                        └── EvidenceChainGateway → FISCO
```

关键变化：**生成请求由后端发起，后端解析 ComfyUI 返回的 history，自己提取参数并落库。** 前端只负责发起和轮询业务任务状态。这一步做完，"自动采集"才名副其实。

### 4.3 新增 `generation_job` 设计

```sql
CREATE TABLE IF NOT EXISTS generation_job (
  id                 BIGINT PRIMARY KEY AUTO_INCREMENT,
  user_id            BIGINT       NOT NULL,
  work_id            BIGINT       NULL,
  version_id         BIGINT       NULL,
  prompt_id          VARCHAR(64)  NULL COMMENT 'ComfyUI prompt_id',
  status             VARCHAR(16)  NOT NULL COMMENT 'QUEUED/RUNNING/SUCCEEDED/FAILED',
  request_json       LONGTEXT     NOT NULL COMMENT '实际提交的工作流',
  request_hash       CHAR(64)     NOT NULL,
  params_json        LONGTEXT     NULL COMMENT '从 history 反解的参数',
  output_file        VARCHAR(255) NULL,
  output_hash        CHAR(64)     NULL,
  error_message      VARCHAR(500) NULL,
  started_at         DATETIME     NULL,
  finished_at        DATETIME     NULL,
  created_at         DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP,
  KEY idx_user (user_id),
  KEY idx_prompt (prompt_id)
);
```

接口契约：

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| POST | `/api/generation/submit` | 提交生成，返回 `jobId` |
| GET | `/api/generation/{jobId}` | 轮询状态，成功后返回 workId/versionId/dataHash |
| POST | `/api/generation/{jobId}/retry` | 失败重试，生成新 job 而非覆盖旧记录 |
| GET | `/api/generation/list` | 我的生成记录 |

实现要点：
1. 后端持有 ComfyUI 地址配置，前端不再暴露 8188。
2. 提交前把工作流 JSON 存一份并算 `request_hash`，作为"我确实提交了这个工作流"的凭据。
3. 轮询 `history/{prompt_id}`，成功后下载 `view` 输出，服务端算哈希。
4. 参数从 history 的 `prompt` 节点中按已知节点 ID 反解，解不出的字段留空并在清单中标注 `unresolved`，不猜。
5. 生成失败也落库，保留 `error_message`，这是"真实执行过"的证据之一。

### 4.5 哈希与签名规则（必须固定，否则验证失效）

| 对象 | 计算方式 |
| --- | --- |
| 文件哈希 | `SHA-256(文件字节)` |
| 规范化 JSON | 键名升序、UTF-8、无多余空白、时间统一 ISO-8601 |
| `dataHash` | `SHA-256(规范化 JSON)` |
| 版本哈希 | `SHA-256(workId|versionNumber|fileHash|parentVersionId|changeDescription)` |
| 协议哈希 | `SHA-256(规范化协议内容)` |
| 签名 | `RSA-SHA256(私钥, 待签内容)`，公钥随用户公开 |

清单里必须写清 `hash_algorithm`、`canonicalization`、`signature_algorithm` 三个字段，否则第三方无法独立复算。

### 4.6 FISCO 适配层契约

当前接口：
```java
public interface EvidenceChainGateway {
    String mode();
    ChainAnchor anchor(String dataHash, String dataType, String description);
    ChainAnchor query(String dataHash);
}
```

pending 实现返回 `status=pending`，绝不伪造交易哈希。

与合作方对接时需要补齐：

| 能力 | 输入 | 输出 | 备注 |
| --- | --- | --- | --- |
| 存证锚定 | `dataHash`, `dataType`, `owner`, `timestamp` | `txHash`, `blockNumber`, `status` | 已有接口 |
| 协议公示 | `agreementHash`, `participants`, `ratios` | `txHash` | 需新增 |
| 结算凭证 | `orderId`, `revenueEventId`, `amount`, `splits` | `txHash` | 需新增 |
| 链上查询 | `dataHash` / `txHash` | 链上记录 | 需新增 |
| 失败重试 | job 表 + 定时任务 | 最终一致 | 需新增 |

设计原则：**链上失败不能阻塞业务**。业务先落库，链上异步补写，状态机为 `PENDING → SUBMITTED → CONFIRMED / FAILED`。

### 6.1 功能验收

| 编号 | 场景 | 通过标准 |

5. 能否诚实说明链上状态（pending）与下一步计划。
