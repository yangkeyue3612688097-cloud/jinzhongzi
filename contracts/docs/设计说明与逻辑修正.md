# 设计说明与逻辑修正报告

> 用途：结项材料 / 金种子答辩 / 给导师汇报"为什么合约要重写"
> 一句话结论：v0.1 的问题不是代码写错，而是**模型没落地**——公式只写在论文里，链上没有算，所谓"分润"其实是一次性按人工填的比例转钱。

---

## 一、v0.1 的 5 个硬伤（逐条给证据）

| # | 问题 | 代码位置（v0.1） | 后果 |
|---|---|---|---|
| 1 | **公式根本没上链**。`anchorContributionResult` 只把 `contributors/weights` 打进 event，链上不存；`distributeProfit` 又让调用方重新传一份任意的 `contributors/weights` | `AICreationProfitSplit.sol:72-96` | 申报书里的 CI 公式（S1/S2/S3）在系统里完全不存在，"分润"只是把人工拍的比例转出去，可复核性为 0 |
| 2 | **分润调用会必然失败**。`distributeProfit` 结尾调用 `evidenceContract.setWorkStatus(...)`，但分润合约不是 evidence 的 admin，`onlyAdmin` 直接 revert | `AICreationProfitSplit.sol:126` | 整笔分润回滚，链上跑不通（这就是"测试网完整验证没做完"的真实原因） |
| 3 | **一次性结清**。`workProfitSettled[workId] = true` 后该作品永远不能再分 | `AICreationProfitSplit.sol:124` | AIGC 作品是多次授权、多次变现的，第二轮收入无处可去；与"版税/持续分润"的商业模型冲突 |
| 4 | **push 转账**。循环 `call{value:...}` 直接打款 | `AICreationProfitSplit.sol:117-122` | 任一地址失败（合约钱包、黑名单、gas 不足）整批回滚，且 20 人时 gas 不可控 |
| 5 | **没有异议环节 + 整除留尘埃**。权重按 `amount*w/10000` 整除，残值留在合约里没人能取 | `AICreationProfitSplit.sol:112-115` | 平台可单方面定比例，协作者无申诉通道；资金滞留 |

另外存证侧的问题：

- 证据之间**没有链式关联**，只是 5 个字段的哈希堆叠。删掉中间一条、调换两条顺序，链上完全看不出来 —— 这不叫"时序哈希链"，申请书里承诺的"链式溯源"没有实现。
- 没有角色模型，`_addContributor` 谁写证据谁就是贡献者，**无法表达"创意发起 / 提示词 / 编辑 / 运营"的职责边界**。
- 没有"本人确认"，创作者可以把路人甲挂进来分钱，也可以把实际贡献者排除在外。

## 二、v0.2 的模型：存证一条链，分润一张表

### 2.1 存证：三层锚定 + 真·时序哈希链

```
输入层  inputRoot = H(初始提示词 + 创作意图)          ← createWork 时锚定，自动生成第 1 条证据
   ↓
过程层  chainHash_i = H(workId, evidenceId, etype, dataHash,
                        operator, timestamp, chainHash_{i-1})   ← 每条证据绑定前一条
   ↓
结果层  resultHash = H(最终成品) 且与链头 processRoot 绑定   ← finalizeWork 时闭合
```

为什么这样改才有意义：

1. **顺序不可篡改**：改任何一条的 `dataHash`，它的 `chainHash` 变，后面所有 `chainHash` 全变，链头对不上。`verifyChain(workId)` 一次重放就能定位到第几条断了。
2. **不可插入 / 不可删除**：新证据的 `prevChainHash` 必须等于当前链头，想在中间插一条，链头就断了。
3. **成本可控**：链上只存 32 字节哈希 + 索引，原文放 IPFS/OSS，`uri` 定位。

> 这份"链"由合约自己维护，不依赖任何中心化服务，第三方可以拿链下原文 + 公开的哈希规则独立复算。

### 2.2 分润：份额表 + 收益托管 + 多轮结算

```
评分上链            收益入托管              结算                   提取
lockShares   →   depositRevenue(msg.value)  →   settle()   →   withdraw()
(CI 计算+快照)      (谁都能付，纠纷期也能收)     (任何人可触发)      (各自领取)
```

三个关键设计：

- **份额表只锁一次，收益可以结算无数次**。第一次变现、第二次授权、第三次商用，都按同一张表分 —— 这才是"版税"。
- **托管 + Pull 支付**：结算只改 `pendingWithdrawals` 记账，用户自己来提。付款方永远成功，收款方互不影响。
- **公示异议期**（默认 3 天）：份额上链后协作者可以 `consentShares` 确认，全员确认可立即结算；有人 `objectShares` 就冻结，交仲裁。对应申请书"异常协作与纠纷处理机制"。

### 2.3 状态机（单一事实来源）

```
Draft ──finalizeWork──> Finalized ──首次结算──> Settled
  │                        │  ↑                    │
  │                        │  └──resolveDispute────┤
  └──(不可逆)              └──raiseDispute──> Disputed ──> Revoked
```

作品状态只存在存证合约里，分润合约每次结算都去读，避免两套状态不一致（v0.1 就是因为两边各记一套才出的 bug）。

## 三、公式怎么落到链上（这是核心）

### 3.1 原公式

```
S1 = α × (W11·S11 + W12·S12)        α∈[0,1]，最终采纳版本 α=1，试验版本 α<1
S2 = λ × (W21·S21 + W22·S22)        λ∈[0,1]，无效迭代越多 λ 越小
CI = W1·S1 + W2·S2 + W3·S3          W1+W2+W3=1，W1∈[0.5,0.6]
分润比例_i = CI_i / ΣCI
```

### 3.2 上链障碍与解法

Solidity 没有浮点。做法：**全程 1e4 定点整数**（`10000 == 100.00 分`，`5000 == 0.5000`），每一步除法向下取整。

```solidity
// ContributionMath.sol
uint256 inner = (w11 * s11 + w12 * s12) / BPS;   // 归一到 [0,10000]
uint256 s1    = (alpha * inner) / BPS;           // 再乘采纳因子
uint256 ci    = (w1*s1 + w2*s2 + w3*s3) / BPS;
```

精度分析：两步除法各最多损失 1 个最小单位（= 0.0001 分），CI 的最大误差 < 0.0003 分，对分润金额的影响远小于 1 wei。**完全确定性**，链上链下用同一套整数运算结果必然一致（`test/ScoringIntegration.test.js` 里用 BigInt 镜像实现交叉验证过）。

分润换算不额外转比例，直接用

```
amount_i = net × CI_i / ΣCI
```

并做两件事：① 余数补给 CI 最大的那位，保证 `Σamount_i == net`（零滞留）；② 平台服务费单独切出（默认 5%，上限 10%）。

### 3.3 一个真实算例（`scripts/demo-e2e.js` 输出）

参数：W1=0.55 W2=0.25 W3=0.20，W11=0.4 W12=0.6，W21=W22=0.5，平台费 5%
收益 1 ETH：

| 角色 | S1 | S2 | S3 | CI | 分润比例 | 实得 |
|---|---|---|---|---|---|---|
| 创意发起 | 79.60 | 69.35 | 75.00 | 76.11 | 26.18% | 0.2488 ETH |
| 提示词设计 | 92.80 | 87.22 | 82.00 | 89.24 | 30.70% | 0.2917 ETH |
| 后期编辑 | 61.20 | 73.80 | 72.00 | 66.51 | 22.88% | 0.2174 ETH |
| 运营推广 | 45.76 | 57.80 | 96.00 | 58.81 | 20.23% | 0.1922 ETH |

平台费 0.05 ETH，四人合计 0.95 ETH，`0.05 + 0.95 = 1.00`，一 wei 不差。

## 四、一个公式落不了地的问题，必须提前解决

**S11/S12 是按提示词定的，那编辑和运营怎么办？**

如果照字面实现，编辑者的 `S11=0, S12=0`，核心维度直接归零，而核心维度权重占 55% —— 意味着编辑和运营哪怕干得再多，也拿不到应得的份额。这是原公式应用到多角色场景时最容易翻车的地方，也是"分润不公平"投诉的主要来源。

v0.2 的处理（写在 `scripts/scoring-engine.js`）：

> **S11 重新定义为"该角色核心产出物的质量"**，而不是狭义的"提示词质量"：
> - 创意发起 / 提示词设计 → 评提示词（结构要素命中、篇幅适配、迭代深度）
> - 模型方 → 参数完备性（是否有 Parameter 证据 + 配套生成）
> - 生成执行 → 有效生成产出量
> - 后期编辑 → 编辑工作量 × 采纳率
> - 运营推广 → 素材与发布产出
>
> **S12 保持通用语义"版本采纳"**：最终版本是否出自你、历史采纳率多少。

这样公式结构一字不改（三个维度、同样的权重约束），只是把 S11 的**测量对象**按角色泛化，既守住申请书口径，又能真的算出来。

## 五、与申请书的对应关系（答辩可以直接照着讲）

## 六、安全性清单

| 风险 | 处理 |
|---|---|
| 重入攻击 | `nonReentrant`（结算、提现）+ 先清零再转账（Checks-Effects-Interactions） |
| 越权 | `admin` / `arbiter` / `scorer` / `settler` 四权分离；管理员转移需两步确认 |
| 抢跑 / 乱改份额 | 份额锁定后不可改（除非结算前版本重算）；异议期内不能结算 |
| 资金卡死 | 托管制 + Pull 提取；`markSettled` 用 try/catch，运营漏配白名单也不影响分钱 |
| 恶意消耗 Gas | 协作者上限 20、单作品证据上限 300，循环有界 |
| 被挂名分钱 | 角色需本人 `acceptRole` |
| 平台单方面改比例 | 异议期 + 仲裁驳回/维持 |
| 误操作 | `pause()` 紧急暂停（不影响已托管资金提取） |

## 七、已知边界（写出来比藏着好）

1. **评分输入仍需信任链下引擎**。合约只保证"输入 → CI → 金额"这一步可复算，`S11..S3` 由平台评分服务产出。要彻底去信任，下一步给评分结果加协作者签名（EIP-712），或引入第三方评分节点。这是 v0.3 的活。
2. **S3 依赖平台运营数据**（销量、授权次数），目前由平台录入，属于半中心化环节。
3. **首次结算后份额表冻结**。若事后发现分润错误，只能通过后续轮次补偿或线下处理，合约不追溯已分配资金（这是有意的：已分配资金不可回滚，才能让收款方敢收）。
4. **未做 Merkle 批量锚定**。当前一条证据一次交易，Gas 约 24 万；申请书里规划的 Merkle 聚合可以把 N 条证据压成 1 次锚定，属于性能优化项。
5. **未接 Stable Diffusion 实时采集**。目前证据由前端/插件按节点上报，`docs/前后端对接指南.md` 里给了采集时机建议。
