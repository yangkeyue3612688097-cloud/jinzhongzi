# AI 创作协作确权与分润平台：阶段性方案

> 本文是阶段方案。当前实际实现、比赛口径和 FISCO 对接清单以 `docs/COMPETITION-READINESS.md` 为准。

> 版本：v2.0  
> 日期：2026-10-31  
> 本文用于比赛答辩、指导老师评审和后续开发拆解。

## 1. 结论

采用以下模式可行，而且比“系统固定算比例”更适合这个项目：

> 协作者协商比例 + 系统可选给出建议 + 全体成员逐人签名确认 + 业务库留存完整版本 + 区块链锚定协议与结算凭证

系统建议只能作为参考，不能直接生效。最终比例必须由协作者确认，任何比例修改都必须生成新版本并由全体成员重新确认。

区块链的作用应从“给一张图片存一个哈希”提升为记录完整责任链：

1. 作品生成参数和输出文件哈希；
2. 作品版本及变更哈希；
3. 全体成员确认的协作协议版本；
4. 收入事件；
5. 按照某个协议版本生成的结算凭证；
6. 上述数据的交易哈希、区块号和链上校验结果。

区块链负责证明“什么时间存在过什么数据、由哪些主体确认过”，不负责判断艺术价值、贡献比例或法律著作权归属。

## 2. 产品定位

### 2.1 一句话定位

面向 AI 创作者和 2-10 人创作团队的“生成来源存证、协作确权、协议分润、公开验证”平台。

### 2.2 不是通用 AI 绘图工具

产品不直接与 Midjourney、Stable Diffusion WebUI 或在线绘图平台竞争。ComfyUI 是来源数据采集端，业务系统负责：

- 证明生成参数与输出文件的绑定关系；
- 管理作品版本和变更证据；
- 固化协作关系与协议版本；
- 按收入事件和协议版本生成分账流水；
- 向买方、评委和第三方提供公开验证入口。

### 2.3 核心用户与需求

| 用户 | 真实需求 | 平台提供 |
| --- | --- | --- |
| 独立 AI 创作者 | 证明作品来源、参数和版本演进 | 生成记录、文件哈希、来源清单、PDF 证书、公开验证页 |
| 2-10 人创作团队 | 说清谁参与、按什么比例分、何时改过协议 | 邀请成员、协议版本、逐人确认、签名记录、协商历史 |
| 团队负责人 | 收入确认后按已确认协议结算 | 授权订单、收入事件、协议快照、分账流水、防重复结算 |
| 买方/甲方 | 核对收到的文件是否与存证版本一致 | 文件哈希复核、来源清单、版本验证 |
| 评委/第三方 | 不依赖平台口头说明即可核验 | `/verify/:hash`、签名状态、链上状态、交易哈希 |

## 3. 核心业务规则

### 3.1 比例由协作者决定

最终协议必须满足：

- 包含当前全部有效协作者；
- 每位协作者的整数比例大于 0；
- 所有比例合计 100%；
- 每位协作者本人确认；
- 全部确认后协议才能生效；
- 任何比例、成员或条款变化都创建新版本，不覆盖旧协议。

建议在后端使用万分比保存，例如 `5000` 表示 50%，避免小数精度问题。比赛阶段可以继续使用整数百分比，但接口应预留升级空间。

### 3.2 系统建议不是算法裁决

建议分为三档：

| 模式 | 用途 | 是否生效 |
| --- | --- | --- |
| 不提供建议 | 完全由发起人填写 | 否 |
| 平均建议 | 按参与人数给出一组初始值 | 否，必须可编辑 |
| 贡献证据提示 | 根据版本、任务、材料提交记录给出提示 | 否，只展示计算依据 |

如果实现“贡献证据提示”，第一版也只使用容易解释的数据，例如确认版本数、已登记任务数和材料数。不要用模型打分直接决定分润，否则无法说明公平性和抗操纵性。

### 3.3 协议版本与收入事件绑定

协议可以修改，但收入发生时适用的协议必须被冻结：

1. 订单确认收款时生成 `revenue_event`；
2. 该收入事件同时记录当时生效的 `agreement_id`、`agreement_hash` 和版本号；
3. 分账时使用收入事件绑定的协议，不使用“当前最新协议”；
4. 新协议只对之后产生的收入事件生效；
5. 结算完成后生成不可重复的 `settlement_receipt`，记录每个成员金额和协议版本。

这条规则解决常见的争议：先收款，后改比例，再用新比例分旧收入。

### 3.4 协议状态机

```text
DRAFT
  -> PENDING
  -> EFFECTIVE
  -> SUPERSEDED

PENDING
  -> REJECTED
  -> COUNTER_PROPOSED
```

新协议在完成全体确认前，不应破坏历史收入和已生效协议的验证。待新协议生效后，旧协议标记为已替代，但历史协议、签名和对应收入仍可查询。

## 4. 推荐的完整流程

### 4.1 生成与作品存证

```text
后端调用本地 ComfyUI
  -> 保存真实工作流、prompt、negative prompt、模型、seed、steps、CFG、尺寸、采样器
  -> 后端下载输出文件并计算 SHA-256
  -> 规范化参数与文件信息，计算 dataHash
  -> 创作者签名
  -> 写入本地业务库
  -> 异步锚定链上
  -> 生成来源清单和证书
```

当前前端可直接访问 ComfyUI，参数仍属于“客户端声明”。正式答辩前应让后端发起 ComfyUI 请求，或者至少明确演示边界，不能把客户端提交的参数描述成服务端独立观测的数据。

### 4.2 协作协议

```text
负责人发起协议
  -> 系统可选填入建议比例
  -> 协作者接受、拒绝或提出反提案
  -> 新提案形成新版本
  -> 每位成员对本版本规范 JSON 签名
  -> 全部签名验证通过
  -> 协议生效
  -> 协议哈希和签名摘要异步锚定
```

### 4.3 收入与分账

```text
创建授权订单
  -> 确认收款
  -> 生成唯一收入事件，同时快照协议版本
  -> 创建结算凭证
  -> 按收入事件绑定的协议版本生成成员分账
  -> 同一收入事件禁止重复结算
  -> 结算凭证哈希异步锚定
```

## 5. 区块链边界

### 5.1 应上链的数据

| 类型 | 上链内容 | 不直接上链 |
| --- | --- | --- |
| 作品存证 | `dataHash`、文件哈希、作品/版本标识、时间 | 原图、完整 prompt |
| 协议锚定 | `agreementHash`、协议版本、参与者地址摘要、签名根 | 个人身份信息、聊天内容 |
| 收入锚定 | `revenueEventHash`、订单标识摘要、金额摘要 | 买方隐私、真实银行流水 |
| 结算锚定 | `settlementReceiptHash`、协议哈希、分账结果摘要 | 私钥、账户密码 |
| 审计锚定 | 日志批次 Merkle 根，可选 | 每一条普通操作日志 |

### 5.2 业务库与链的权威边界

```text
业务数据库：业务事实和当前状态
区块链：不可篡改的证明和事件顺序
```

链上失败不能阻断上传、协议确认和本地分账。采用事务外盒（outbox）：

```text
业务事务写入 chain_anchor(status=PENDING)
  -> 后台任务提交链上交易
  -> SUBMITTED
  -> CONFIRMED / FAILED
  -> 失败可重试，页面如实展示状态
```

### 5.3 合约选择

合作方的 `AICreationProfitSplit` 通过 CI 指标自动计算比例，与本项目的协商比例模型存在规则冲突，不应作为比赛主线的最终裁判。

建议分两条能力接入：

1. 作品证据：在 FISCO 兼容性确认后接入 `AICreationEvidence` 的 `createWork`、`addEvidence`、`finalizeWork`、`verifyChain`。
2. 协议与结算：新增最小 `BusinessAnchor` 合约，只记录业务类型、业务 ID 哈希、数据哈希和元数据 URI。

建议接口：

```solidity
function anchor(
    bytes32 businessId,
    bytes32 dataHash,
    uint8 businessType,
    string calldata metadataURI
) external returns (uint256 anchorId);
```

业务类型：

```text
1 = agreement
2 = revenue_event
3 = settlement_receipt
4 = audit_checkpoint
```

不要把协作协议伪装成 `EvidenceType.Edit`。这会让链上语义和业务语义不一致。

## 6. 新增数据模型

### 6.1 协议增强字段

在现有 `collaboration_agreement` 基础上增加：

```text
proposal_source       MANUAL / EQUAL_HINT / CONTRIBUTION_HINT
ratio_basis           比例依据说明
supersedes_id         替代的旧协议
signature_root        成员签名集合的摘要
chain_anchor_id       对应链上锚定记录
```

提案规范 JSON 至少包含：

```json
{
  "schema": "aic-collaboration-agreement/v2",
  "collaborationId": "15",
  "workId": "11",
  "workVersionHash": "...",
  "version": "3",
  "proposalSource": "MANUAL",
  "ratioBasis": "双方协商确认",
  "supersedes": "2",
  "participants": [
    {"userId": "17", "ratioBps": "5500"},
    {"userId": "6", "ratioBps": "4500"}
  ],
  "nonce": "..."
}
```

### 6.2 收入事件快照字段

为 `revenue_event` 增加：

```text
agreement_id
agreement_hash
agreement_version
```

收入事件创建后，这三个字段不可修改。

### 6.3 链上锚定表

```sql
CREATE TABLE chain_anchor (
  id BIGINT PRIMARY KEY AUTO_INCREMENT,
  business_type VARCHAR(32) NOT NULL,
  business_id BIGINT NOT NULL,
  business_hash CHAR(64) NOT NULL,
  chain_mode VARCHAR(32) NOT NULL,
  contract_address VARCHAR(128),
  chain_record_id VARCHAR(128),
  tx_hash VARCHAR(128),
  block_number BIGINT,
  status VARCHAR(16) NOT NULL,
  retry_count INT NOT NULL DEFAULT 0,
  error_message VARCHAR(500),
  created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  confirmed_at DATETIME,
  UNIQUE KEY uk_business (business_type, business_id, business_hash)
);
```

### 6.4 结算凭证

新增 `settlement_receipt`：

```text
id
order_id
revenue_event_id
agreement_id
agreement_hash
total_amount
splits_json
receipt_hash
chain_anchor_id
created_at
```

`order_id` 和 `revenue_event_id` 应设置唯一约束，防止重复分账。

## 7. 分阶段开发计划

### P0：业务规则收口（1-2 天）

目标：先保证不接链也能公平、可解释地结算。

任务：

- 协议继续支持协商比例，不做固定 50/50；
- 增加“系统建议”标识，但建议必须可编辑；
- 新协议确认前不破坏历史协议和历史收入；
- 收入事件创建时快照协议 ID、版本和哈希；
- 分账改为按收入事件绑定的协议执行；
- 新增收入事件唯一约束和结算凭证；
- 补充协议权限、重复确认、重复结算、旧收入使用旧协议等测试。

验收：

- 1000 元收入产生时绑定协议 v2（60/40）；
- 协议改为 v3（50/50）后，这笔旧收入仍按 v2 分为 600/400；
- 新收入产生后按 v3 分配；
- 同一订单第二次分账被拒绝；
- 协议详情能查看版本、比例、确认人和签名状态。

### P1：协商与反提案体验（2-3 天）

目标：让“协作者自己决定”成为真实可演示的流程。

任务：

- 负责人发起提案；
- 全体成员都能查看建议依据；
- 协作者可接受、拒绝或提出反提案；
- 反提案自动创建新版本；
- 前端展示版本时间线和每个人的确认状态；
- 增加“协议签名验证”接口和页面提示；
- 明确当前签名为平台托管 RSA 签名，不冒充链上钱包签名。

验收：

- 负责人提出 60/40；
- 协作者提出 55/45 反提案；
- 负责人确认反提案后协议生效；
- 旧提案保留为历史，不可篡改；
- 非参与成员无法确认。

### P2：链上锚定基础设施（2-3 天）

目标：链失败不影响业务，但链状态不会被伪造。

任务：

- 新建 `chain_anchor` 表和 outbox 服务；
- 状态机实现 `PENDING -> SUBMITTED -> CONFIRMED / FAILED`；
- 重写现有 `EvidenceChainGateway`，不再使用不存在的 `saveEvidence` 文档接口；
- 先接本地 Hardhat 测试合约或 FISCO 测试网络；
- 保存 `txHash`、区块号、合约地址和链上记录 ID；
- 验证页分别展示“本地校验”“签名校验”“链上校验”。

验收：

- 关闭链服务时业务仍然完成；
- `chain_anchor` 保持 `PENDING/FAILED`，页面不显示假交易哈希；
- 链恢复后可重试并转为 `CONFIRMED`；
- 交易哈希和区块号可查询。

### P3：协议、收入、结算上链（2-3 天）

目标：让区块链真正贯穿协作和分账。

任务：

- 协议生效后锚定协议哈希；
- 收款后锚定收入事件哈希；
- 结算后锚定结算凭证哈希；
- 公开验证页展示业务哈希、交易哈希、区块号和链上完整性；
- 作品证据优先对接合作方 `AICreationEvidence`；
- 协议和结算对接 `BusinessAnchor`，不混用 CI 分润合约。

验收：

- 一次完整流程至少产生协议、收入、结算三类锚定记录；
- 修改本地协议文本后，与链上哈希不一致会被发现；
- 评委可以从公开页面看到成员比例、协议版本、结算金额摘要和链上状态。

### P4：可信生成与答辩收口（2-4 天）

目标：把“来源存证”从客户端声明升级为服务端观测。

任务：

- 新增 `generation_job`；
- 前端调用业务后端，不直接暴露 ComfyUI；
- 后端提交工作流、轮询 `history`、下载输出、计算哈希；
- 保存真实工作流 JSON、prompt、negative prompt、模型、seed、steps、CFG、尺寸、采样器；
- 失败任务也留痕并支持重试；
- 修复版本越权、版本哈希不同步、审计 IP 为空等 P0 安全问题；
- 固化比赛演示账号、数据、断网兜底录屏。

验收：

- 关闭前端直连 ComfyUI 的代理后仍能通过后端生成；
- 前端篡改参数不会改变后端记录；
- 每个作品和版本都能分别验证；
- 生成失败也有任务记录和错误原因。

## 8. 比赛演示建议

### 8.1 八分钟演示主线

1. 用账号 A 展示作品 v1 的 ComfyUI 参数、文件哈希、证书和公开验证页；
2. 上传 v2，展示版本哈希和当前版本切换；
3. 邀请账号 B 加入协作；
4. 系统给出 50/50 建议，A 改为 60/40；
5. B 不接受并提出 55/45 反提案；
6. 双方逐人确认，系统显示签名验证通过和协议哈希；
7. 展示协议链上锚定的交易哈希和区块号；
8. 创建 1000 元订单并确认收款，展示收入事件快照协议 v2；
9. 分账为 550/450，展示结算凭证和链上锚定；
10. 再点一次分账被拒绝；
11. 修改本地文件后，公开验证页提示哈希不一致。

### 8.2 答辩时必须说清楚的边界

- 比例是协作者协商结果，不是系统算法裁决；
- 系统建议不直接产生法律或结算效力；
- 区块链证明数据存在和未被篡改，不直接确认著作权；
- 当前支付是人工确认收款，不是银行支付回调；
- 当前签名为平台托管签名时，不能宣称是用户独立钱包签名；
- FISCO 未实际接通时，必须显示 `pending`，不能展示伪交易哈希。

## 9. 当前实现与目标状态

### 9.1 已经具备

- 本地注册登录与平台托管 RSA 签名；
- 作品上传、ComfyUI 参数采集、文件哈希、来源清单和 PDF 证书；
- 公开验证页；
- 作品版本创建、确认和当前版本切换；
- 协作邀请；
- 协商比例协议、版本号、逐人确认、合计 100% 校验；
- 订单、人工确认收款、唯一收入事件、按协议分账、防重复结算；
- 关键操作审计日志。

### 9.2 仍需补齐

- 收入事件未快照协议版本；
- 协议尚无接受、拒绝、反提案交互；
- 链上状态仍为 `pending`，没有真实适配器；
- 协议、收入、结算尚未锚定；
- ComfyUI 仍由前端直连，生成参数属于客户端声明；
- 版本证据尚未完全独立；
- 多个作品、订单、协作接口仍缺少参与方授权校验；
- 审计日志 IP/UA 为空，失败写入可能被吞掉；
- 当前 `blockchain_address` 不是可用于签链上交易的 secp256k1 账户。

## 10. 最终完成定义

当下面五个条件同时满足时，可以认为项目形成比赛可交付闭环：

1. 生成参数由业务后端从本地 ComfyUI 真实取得；
2. 作品、版本、协议、收入、结算都有稳定规范 JSON 和哈希；
3. 协议比例由全体参与者逐人确认，任何修改形成新版本；
4. 每条收入绑定其发生时的协议版本，并能生成不可重复的结算凭证；
5. 关键证据、协议、收入、结算在链上可查，公开验证页能区分本地状态、签名状态和链上状态。
